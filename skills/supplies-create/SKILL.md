# Поставка FBO: план → черновик → заявка → грузоместа → таймслот

Маршрут: **0** готовые Super-заявки → **1** вопросы → **2** что лежит и едет → **3** план → **4** черновик и расчёт →
**5** план перед заявкой → **6** заявка и сверка → **7** грузоместа и таймслот → **8** приёмка, этикетки, отчёт.

| Просьба | Что делать |
|---|---|
| «подай поставку», «отправь товар на склады» | весь маршрут |
| «посчитай, сколько везти» | шаги 0–5, заявку не создавать |
| «докинь N штук в <город>», «довези в Питер» | новая заявка на один кластер (шаги 3–8): кластеры поданной заявки Ozon не меняет |
| «заявки уже подал, распредели» | «Заявка уже подана» ниже |
| «заполни грузоместа», «округли по коробкам», «убери коробку» | навык `supplies-cargoes` |
| «ошибся в заявке», «поменяй слот», «отмени», «укажи водителя», «поправь количество», «перепечатай этикетки» | навык `supplies-orders`: одна команда, маршрут не проходить |
| «что подано», «сколько едет», «нет ли дублей» | только чтение: `supplies_orders_list` `tab=preparation`; `supplies_items_list` (`sku`, `active=true`) → `python3 scripts/supply_plan.py pending`; дубли (совпали товар, кластер, точка, дата) — показать, отмена только явным «да» |
| серия Super-заявок в запас без таймслота | навык `supplies-super` |
| точный объём из поданных Super-заявок | навык `supplies-kits` |

## Согласие

- **Полная просьба — согласие подать**: названы товар, объём, фасовка, точка отгрузки, срок годности и дата (или
  «ближайший подходящий слот»). Заявка, грузоместа и таймслот — без остановок, потом отчёт. Разведку и проверки делать
  всегда.
- **Один вопрос одним сообщением**: чего-то не хватает или неоднозначно (шаг 1); кластеры не примут товар или примут
  часть (шаг 5); Ozon урезал объём или убрал города (шаг 7); объём не кратен коробке; запас выходит на сотни дней.
- **«Делай сам»** — эти решения агент принимает сам методом навыка и называет в отчёте; недобор больше 15 % от просьбы —
  всё равно спросить. **«Покажи план перед подачей»** — остановиться на шаге 5.
- Отмена заявки (`supplies_orders_cancel`, необратимо) — только после явного «да» (навык `supplies-orders`).
- Голосовое сообщение путает цифры и названия («2000 коробок» вместо штук): проверить коробки × штук = итог, назвать, как понято, и
  подтвердить одним вопросом; «делай сам» по голосу не включать.

## Найти товар и заявки

- Сначала искать, потом спрашивать: товар, точку и заявки найти до вопроса и спросить всё одним сообщением.
- Заявки — `supplies_orders_list` (`search` — номер вида `12345678-1`; `tab`: `preparation` — «в заполнении», «готова»,
  «собрана»; `in_transit` — «сдал в хаб», «едет», «принимают»; `acts` — «акт», «расхождения»; `archive`) и
  `supplies_items_list` (`sku`).
  «Черновик» — ещё и `supplies_drafts_list`.
- **Статус поставки ≠ статус заявки.** У частично отгруженной заявки (`IN_TRANSIT`, `REPORTS_CONFIRMATION_AWAITING`)
  бывают готовые поставки (`READY_TO_SUPPLY`). Поставки фильтровать по их статусу — `supply_states`, не `states`.

## Черновики, расчёт, команды

- `supplies_drafts_create`, `supplies_drafts_update`, `supplies_drafts_delete` — данные Seller AI, Ozon не трогают.
  `supplies_drafts_calculate` создаёт невидимый черновик Ozon и тратит квоту: 2 расчёта в минуту, 50 в час, 500 в сутки
  на аккаунт; повтор той же ревизии — прежний расчёт без квоты.
- SKU, номер заявки, точку и срок годности брать только из инструментов или от пользователя, не из примеров. Скрипты
  запускать самому; пользователю — цифры и результат.
- 422 `sku_not_in_catalog` — карточки с таким SKU нет и у Ozon. 409 `stale_expected` — в Ozon уже не то, что видел
  пользователь: перечитать, показать, спросить заново. 409 `target_busy` — идёт другая команда: дождаться её
  (`operations_get`), вторую не слать. `local_quota` с `retry_at` — исчерпан лимит создания заявок: назвать время.
- Прочие коды — [references/errors.md](references/errors.md).

## Шаг 0. Готовые Super-заявки того же города

Перед новой подачей проверить, не покрывают ли потребность уже поданные Super-заявки этого SKU и фасовки из того же
города (точка отгрузки в городе любая). «С нуля», «не бери из готовых» — шаг 0 пропустить. «Ровно N шт из готовых»,
«собери комплект», «возьми из поданных по потребности» — навык `supplies-kits`.

1. `supplies_items_list`: `sku`, `super=true`, `supply_states=DATA_FILLING,READY_TO_SUPPLY`, `limit=500`, все страницы
   (`offset`). Не `states`: по статусу заявки готовые поставки частично отгруженных заявок выпадут. По каждой заявке —
   `supplies_orders_get`: `order.tags.super`, `order.dropoff` (город), `order.timeslot` (`null` — не выбран),
   `supplies[]` (кластер, `units`, `state`), `cargoes[]` (фасовка — `items[].quantity` мест).
2. Набор — заявки одного SKU, фасовки и города с непересекающимися кластерами. Сравнить с нужным распределением (шаг 3),
   допуск ± коробка-две на кластер; по кластерам — навык `supplies-kits`, шаги 1 «Кандидаты» и 3 «По потребности» (на
   кластер одна целая поставка, остаток — новой заявкой). Пометить набор в Seller AI нечем: при каждой подаче проверять его заново, блокеры
   тоже.
3. Покрывает — новую заявку не подавать: таймслот на дату пользователя, иначе ближайший подходящий (навык
   `supplies-orders`); сказать «взял из имеющихся Super-заявок» со ссылками; этикетки взятых поставок — шаг 8.
4. Покрывает часть — новой заявкой только недостающее. «Подай» — подать и сказать, что взято из имеющихся, а что подано
   новой заявкой; «посчитай» — предложить.
5. У взятой заявки нет слотов (`slots: []`, `forbidden` пуст) — почти всегда кластер-блокер: найти по навыку
   `supplies-orders` («У заявки нет слотов»). Новые заявки взамен не подавать, старые не отменять: ссылки и блокеры —
   пользователю, убирает их он сам в кабинете, по одному; блокеры по черновику — прогноз. После «убрал» — перечитать,
   поставить слот, выдать этикетки.
6. **«Полностью с нуля».** Начали брать из поданных, а пользователь передумал («давай с нуля», «всё новой заявкой») —
   весь объём просьбы идёт в новый план (шаги 1–8), взятое не вычитать. Поданные заявки остаются, только если так решил
   пользователь; отмена каждой — только явным «да». Оставленные вместе с новой везут больше просьбы — назвать сумму.
   Перед итогом перечислить по этому разговору (не по файлам и заметкам), что уже изменено в Ozon: созданные и
   отменённые заявки, поставки с заменёнными грузоместами (прежние этикетки недействительны — не печатать), поставленные
   таймслоты (непривоз по ним — 0 в «Точности отгрузок»), правки состава.

## Шаг 1. Разведка, потом все вопросы сразу

- Товар — `products_list` с `search` по словам пользователя. Несколько карточек — показать
  `[название](https://www.ozon.ru/product/<sku>)`, остаток FBO и артикул, дать выбрать. `processing: true` или нет `sku`
  — карточка ещё создаётся: подождать с черновиком несколько минут. «Не продаётся» без остатка — норма.
- Точка отгрузки — `supplies_dropoff_points_search` (от 4 символов; ПВЗ — полным названием); несколько — показать
  названия с адресами, дать выбрать. «СЦ <город>» — тип `SORTING_CENTER` (обычно `…_ХАБ`), `…_АППЗ_…` — пункт приёма
  заказов. «Откуда всегда» — точка, с которой этот город уже отгружался (`supplies_orders_list`, вкладки `in_transit`,
  `archive`); таких две — спросить.
- **Город назначения — не точка отгрузки.** «Довези в Питер» — кластер (`supplies_clusters_list` с `search` по городу
  или складу); точку называет пользователь, она одна на заявку. Названы склады («Пушкино или Хоругвино») —
  `supplies_clusters_list` покажет кластер; оба в одном — выбор бессмыслен: склад внутри кластера назначает Ozon.

Чего не назвали — спросить одним сообщением (второй круг вопросов — ошибка):

> Чтобы подать поставку, уточните:
> 1. какой товар везём и сколько всего штук;
> 2. фасовка: сколько штук в коробке и вместимость палеты (если палеты есть);
> 3. срок годности партии;
> 4. дата отгрузки критична или подойдёт ближайший подходящий слот.

- Названо всё — не спрашивать. Режим («покажи план», «делай сам») не спрашивать.
- **Кратность.** `4700 / 12` → показать `391 кор. = 4692 шт (−8)` и `392 кор. = 4704 шт (+4)` и спросить; «делай сам» —
  вниз до целых коробок и назвать.
- Вводные противоречат («только палетами, но коробок по 20 сделай 30») — показать, как поняли, и спросить.
- **Смешанная фасовка** («1 палета 390 шт и 16 коробок по 25»): объём = сумма мест, без округления; палета — одним
  местом в один кластер (`fixed`, шаг 3), остальное — в кратности меньшей коробки. Коробки разных размеров без палеты —
  план в кратности меньшей коробки на объём ≈ сумма коробок, после создания округлить заявку по этим коробкам (навык
  `supplies-cargoes`): у поставки один размер и один срок.
- Поданные, но не отгруженные заявки — не спрашивать (вычитается только отгруженное, шаг 2), если их не заметно много.
- Срок годности в прошлом («01.09.2026» в октябре 2026) — опечатка в годе: заявку готовить, перед грузоместами
  переспросить «срок — 01.09.2027?». Дата без года — ближайшая будущая, год назвать. Тот же товар в другой магазин в том
  же разговоре — тот же подтверждённый срок.
- Та же заявка с другим сроком — новая партия или правка срока поданной: спросить, голое «да» не ответ.
- Метка Super (`is_super`) не доказывает бесплатную доставку.

## Шаг 2. Что уже лежит и едет

1. `supplies_planning_availability` (`view=products`, `skus=<sku>`, `expand=<sku>`, `days=28`) — строки по кластерам:
   `ads` (продажи в день за 28 дней), `available_fbo`, `cluster.id`. `ads: null` — аналитика Ozon не загружена: сказать.
2. Товар на точке отгрузки не виден ни в остатках, ни в `in_transit` — отгруженное считать по заявкам:
   `supplies_items_list` с `sku`, `supply_states=ACCEPTED_AT_SUPPLY_WAREHOUSE,IN_TRANSIT,ACCEPTANCE_AT_STORAGE_WAREHOUSE`
   (для `mode: all` — ещё `READY_TO_SUPPLY,DATA_FILLING`), `limit=100`, все страницы. Строки — в файл (не пересказывать)
   → `python3 scripts/supply_plan.py pending <файл>` с `{"mode", "items": [строки]}`. `mode: shipped` (по умолчанию)
   считает отгруженное, `all` — ещё и поданное (по просьбе). `counted` кластера — в `pending` плана; `in_transit` Ozon
   тогда не прибавлять (двойной счёт). `unknown_cluster_units` больше 0 — назвать штуки без кластера.
3. **Кластеры плана — все кластеры Ozon**: `supplies_clusters_list` (взять только `cluster_id` и `name`), строки п. 1 —
   по `cluster.id`; кластеру без строки — `ads: 0` и остаток 0, сколько ему — решит метод, кто не примет — скажет расчёт.
   СНГ (Алматы, Астана, Беларусь, Армения, Узбекистан) включены; убрать — только если везут лишь по России.

## Шаг 3. План распределения

Цель — равный запас: после поставки каждому кластеру хватит на одинаковое число дней. Метод выбирать по этому SKU
каждый раз заново; назвал пользователь — по его слову.

| Продажи | `method` |
|---|---|
| устойчивые: десятки штук за 28 дней, ADS > 0 в большинстве кластеров, где товар был | `idc` — равный запас в днях |
| в части кластеров ADS = 0, потому что товара там не было | `idc` (скрипт даст им ADS по доле рынка) |
| почти нет: меньше ~30 шт за 28 дней, 1–2 кластера, новая карточка, долгое отсутствие | `market_share` |
| объём больше продаж за 56 дней | `mixed` (потребность на `horizon_days` 28–56 по ADS, остаток по долям) или `market_share` |

`auto`: ADS = 0 или ADS × 56 < объёма — `market_share`, иначе `idc`. Продажи только там, где лежала прошлая поставка, или
скачки ADS (акция, разовый опт) — шум, не повод для `idc`; доли рынка на товаре с устойчивыми продажами — тоже ошибка.

```bash
python3 scripts/supply_plan.py plan plan_input.json
```

- Вход: `total`, `box_size`, `method`, `clusters: [{id, name, ads, available, pending}]`. По желанию: `fixed: {cluster_id:
  штук}` — палета целиком, вне раскладки; `origin` — `coordinates` точки из `supplies_dropoff_points_search` (дни в пути
  уменьшают остаток к приезду; своё число — `travel_days` кластера); `shares` — доли самого магазина в процентах:
  `supplies_planning_sales_by_clusters` (`period=quarter`, `scheme=fbo`), `delivery_clusters[].units / totals.units × 100`.
- Выход: штуки и коробки по кластерам, запас в днях до и после, `share_pct`, `orders` — разбиение по 30 коробок,
  `warnings`; минимум коробка на кластер. `total` не кратен коробке — `variants` вниз и вверх (шаг 1). Доли по умолчанию —
  заказы FBO за 24.07–21.08.2026; Армении и Узбекистана в них нет — их объём задать вручную.

Правила плана:

- **Больше 30 коробок в поставку Ozon не примет** (палет — 40). Не спрашивать: сверх 30 — отдельной заявкой в тот же
  кластер, k-я порция каждого кластера — в k-ю заявку (`orders`), все заявки — на один таймслот. Палеты ради лимита не
  включать; меньше везти — только по прямой просьбе.
- **Палеты.** «N палет по M коробок» — обычно способ посчитать штуки. Палета целиком — только кластеру, которому досталось
  не меньше её вместимости (обычно Москва и Питер); иначе палет не будет — сказать до подачи. До полной палеты не хватает
  ≤ 10 % — можно предложить округлить за счёт других кластеров, если у них останется хотя бы одно место. В отчёте — «из N
  палет K едут целиком, остальные разобрать».
- Пользователь сказал, что палеты не разбираются, — план в палетах: `box_size` = штук на палете, `box_limit: 40`,
  минимум палета на кластер; сказать, что мелкие кластеры получат целую палету. Палету не дробить, коробки на палеты и
  обратно не переключать.
- Запас выходит на сотни дней — до подачи назвать продажи в день, запас и сколько дней добавит поставка. Десятки тысяч
  штук «в заявках» — вероятные дубли, отдельной строкой.
- Малый добор (1–5 коробок) — в 1–2 города с наибольшей потребностью, не «по коробке всем».
- Новый товар без продаж и аналитики: 1–2 коробки — в Москву, на слот соседних заявок этой точки, выбор назвать;
  крупный объём — по долям рынка или по раскладке похожего товара магазина.
- «Та же поставка в другой магазин» — пересчитать по данным того магазина и показать отличия.

## Шаг 4. Черновик и расчёт

1. `supplies_drafts_create`, `body`: `source: manual`, `dropoff: {warehouse_id, type, name, address}` из поиска точки,
   `clusters: [{macrolocal_cluster_id, items: [{sku, quantity, units_per_box}]}]`; до 20 кластеров на черновик, больше —
   несколько черновиков. Переносить каждый кластер плана, включая последний: пропущенный ошибки не даёт, заявка выйдет
   меньше и не поднимется — сверить `totals` с планом. `warnings`: `box_limit` — больше 30 коробок в кластер;
   `single_unit` — 1 шт. (такие заявки Ozon сразу отменяет: указать реальное количество). 422 — причина в
   `items[].code`.
2. `supplies_drafts_calculate` с `body: {revision}`; 202 или `calculation.status` `creating`, `in_progress`, `reading` —
   опрашивать `supplies_drafts_get` раз в 10–20 секунд до `success`, `failed`, `error`. 429 `rate_limited` — повтор
   после `retry_after`; несколько черновиков — по очереди, через 30 секунд. После 429 Ozon расчёт может идти несколько
   минут — Seller AI ждёт сам. `error` с `timeout` или `upstream_error` — не пересчитывать сразу: через минуту
   перечитать `supplies_drafts_get` (новый расчёт — новая квота).
3. `calculation.clusters[]`: `availability` `full` — примет всё, `partial` — `accepted.units` из `requested_units`,
   `none` — не примет (`reason_text`); `super` — кластер даёт Super; `timeslots_allowed` — все примут хоть часть.
   `success` и `full` без количеств ничего не доказывают: смотреть `accepted.items[].quantity` и `restricted`.
4. Есть `none` — убрать эти кластеры `supplies_drafts_update` (новая `revision`) и рассчитать второй раз; бюджет
   заявки — 2 расчёта. Объём убранных сам никуда не переходит: пересчитать план тем же методом по принявшим (все
   кластеры минус `none`) или оставить у продавца — и сказать.
5. Слоты — `supplies_drafts_timeslots_list` (`date_from`/`date_to`, не больше 27 дней; по умолчанию сегодня + 13 дней;
   дальняя дата — окно от неё вперёд). Слоты — точки отгрузки: один список на заявку, в её поясе (`timezone`);
   `from`/`to` передавать как есть. 409 `calculation_required` — расчёт устарел (живёт 30 минут, годен до
   `usable_until`): пересчитать.
6. `no_common_slot: true` — нет общего слота, где-то кластер-блокер: подозрительные кластеры — отдельными черновиками с
   окном ~25 дней, или делить кластеры пополам (каждый расчёт — квота; больше 6 — спросить). Кластер без слотов во всём
   окне убрать, его объём — тем же методом, сказать. Черновики-пробы — `supplies_drafts_delete`.

Доступность зависит от SKU: кластер может не брать товар 500 г и брать тот же товар 1 кг. `INCOMPATIBLE_WAREHOUSE` у
только что созданной карточки — повторить расчёт через 2–3 минуты, прежде чем говорить «город не принимает».

## Шаг 5. План перед заявкой

Заявки ещё нет — последняя точка, где всё меняется бесплатно.

- Просьба полная и расчёт её подтверждает (все примут целиком, объём как назван, кратность сошлась) — подать сразу
  (шаг 6), план — в отчёт.
- Расходится (кто-то не примет или примет часть, палет не будет, запас на сотни дней) или просили показать — показать
  план и спросить один раз. Спросили «Подаём?» — до ответа ничего не создавать. Правки («убери Калининград», «в Москву
  поменьше») — `supplies_drafts_update` и новый расчёт, не план с нуля.

В плане — кластеры (города), не склады: склад внутри кластера Ozon назначит сам. Кластеры и количества (шт / коробок /
палет), итог, метод и запас в днях одной строкой («по продажам — запас ≈ 4 недели на город»; «по долям рынка — за месяц
продано 6 шт, только в Москве и Питере»); кто не примет и почему (`reason_text` словами), кто примет частично; сколько
уходит отдельной заявкой сверх 30 коробок; почему крупный город получил минимум (там лежит прошлая поставка); **это
заявка, а не гарантия** — Ozon может урезать количества, факт виден после создания.

**Таймслот.** По умолчанию заявка создаётся без таймслота: пока его нет, правки количеств не влияют на «Точность
отгрузок»; слот — после сверки состава и мест (шаг 7). Слот сразу, при создании, — только в двух случаях:

- `supplies_accuracy_get` → `rate_percent < 10`: без слота Ozon заявку не создаст — слот на 3–7 дней вперёд, не на
  сегодня;
- дата критична («только 05.11»): слот этой даты, иначе его займут, пока идут сверка и места; правки после слота — с
  `confirm_accuracy`.

## Шаг 6. Заявка и сверка факта

1. `supplies_orders_create`, `body: {draft_id, revision, calculation_id, timeslot: null, confirm: true}` (или
   `timeslot: {from, to}` из списка как есть) — сразу после расчёта, он годен до `usable_until`. 409
   `calculation_required` — пересчитать и подать; `draft_submitted` — создание уже идёт: следить за ним, не подавать
   снова.
   - Несколько заявок (больше 20 кластеров, порции сверх 30 коробок) — черновик и команда на каждую, по очереди. Слот
     для всех — общий: `python3 scripts/supply_plan.py intersect` над ответами `supplies_drafts_timeslots_list`
     (`{"answers": [...]}` → `common[]`, в команду каждого — его строки из `per_answer`); общего нет — спросить, какую
     дату разнести.
   - Подачу прервали — созданное остаётся: найти свежие заявки (`supplies_orders_list`, `sort=created_at`,
     `order=desc`) и назвать. Метод поменялся посреди подачи — сначала решить судьбу созданных, иначе объём задвоится.
2. Итог — `operations_get`. `succeeded`: `order_id` (в `steps[].ozon_reference` или в поле операции) и `collateral` —
   `quantities_cut` (кластер, SKU, было → стало) и `clusters_dropped`. `partial` с `created_with_differences` — создана
   иначе, чем просили: сверить (п. 3). `failed` — причина в `message`, её не придумывать; `TIMESLOT_NOT_AVAILABLE` —
   взять другой слот из свежего списка; `ORDER_ALREADY_CREATED` — не отказ, заявка есть: найти её. `outcome_unknown` —
   Seller AI сам ищет заявку по номеру черновика: ждать.
   **Заявка на один кластер** получает номер без префикса черновика (`2000…`, а не `{draft_id}-1`): при потерянном
   ответе операция может кончиться `failed` `not_created`, хотя заявка есть. Перед новой подачей —
   `supplies_orders_list` (`sort=created_at`, `order=desc`): свежая заявка с этим кластером, товаром и количеством — она.
3. `supplies_orders_get`: `supplies[].units` каждой поставки против плана. **Ozon молча режет количества** по вместимости
   — до сырого лимита, не кратного коробке (636 → 139), или кратно (80 → 60). До сверки объём не обещать: «заявка
   создана, проверяю, сколько прошло».
   - Одиночную поставку Ozon может поднять до своего минимума (1 → 20): срезать до названного, предупредив, что поднять
     назад не выйдет.
   - Некратный остаток «оставить как есть» не предлагать: поднять до плана (п. 4), не вышло — вниз до целых коробок.
   - «Просил X, а в заявке меньше» — по порядку: заявок несколько (сложить все); кластер выпал (`clusters_dropped`) —
     п. 6; остальное срезал Ozon (`quantities_cut`) — п. 4.
4. **Добор — до грузомест**, пока поставка `DATA_FILLING`:
   - поднять срезанный кластер: `supplies_supply_items_set`, `body: {items: [{sku, quantity}], expected: {bundle_id}}`
     (`bundle_id` — из `supplies[]`); до плана не прошло — на коробку меньше;
   - затем — отдельная небольшая заявка на недобор в тот же кластер (живая заявка на этот SKU и кластер не мешает,
     отменять её не нужно);
   - кластер не принимает (расчёт — `none`) — поднять принимающим кластерам тем же методом, что основной план:
     `python3 scripts/supply_plan.py plan` с `total` = просьба и `fixed` = срезанные на их факте; срезал снова — ещё
     круг, не больше трёх. Не досыпать недобор в первый ёмкий кластер;
   - не вышло — отдельной заявкой в 1–2 города с наибольшей потребностью.

   После грузомест увеличение не проходит (`INBOUND_NO_CAPACITY`) — только новой заявкой. Уменьшение проходит всегда,
   но не «на пробу»: вернуть назад Ozon может не дать. Подгонка к названному объёму тем же методом — часть просьбы;
   правка, меняющая объём, города или метод против просьбы, — один вопрос.
5. Срезано ниже коробки (120 → 19 при коробке 20): ноль Ozon не примет, удалить поставку нельзя — «коробку на <город>
   собрать на 19 шт» (полные + одна неполная). Убрать город — только новой заявкой без него и отменой всей старой (навык
   `supplies-orders`): сначала новая, потом отмена, затем убедиться, что старая `CANCELLED`. До этого предложить выбор:
   неполная коробка или пересборка.
6. Выпавшие кластеры не терять молча: назвать, сколько и куда не уехало, и предложить — повторить заявкой на них (часть
   проходит со второй попытки), сдвинуть окно дат, разложить по принявшим или оставить у продавца.

## Шаг 7. Факт → грузоместа → таймслот

Факт (города, количества, коробки и палеты, недобор, все заявки) совпал с просьбой или отличается только подгонкой шага 6
— сразу места и таймслот, факт — в отчёт. Ozon урезал объём или убрал города и добрать не вышло (при «делай сам» —
недобор больше 15 %), поднял одиночную поставку — показать факт и спросить до грузомест: места закрепляют состав, после
них не поднять.

1. Грузоместа каждой поставки — навык `supplies-cargoes` (одна команда `supplies_cargoes_set` на поставку; `packing`
   заявки — `units_per_box` черновика). Места с уже выданными этикетками не перезаполнять: `replace` даёт новые номера,
   выданные этикетки становятся недействительны; часть мест — `add`/`delete`. После добора — места только новой заявки.
2. Таймслот, если его нет, — навык `supplies-orders` (`supplies_orders_timeslots_list` → `supplies_orders_timeslot_set`).
   С первым слотом Ozon начинает считать «Точность отгрузок»: дальше каждое уменьшение и отмена её снижают. Не на сегодня
   (за несколько часов до слота правки закрываются) и не самое раннее окно (его разбирают за секунды): 3–7 дней вперёд,
   днём. Одна дата на все заявки поставки — `python3 scripts/supply_plan.py intersect` над ответами
   `supplies_orders_timeslots_list`. «Дата не важна» — не «ближайший час»: назвать дату и время точки (`local_from`) и
   предложить сдвинуть, если до слота меньше рабочего дня.
3. Водитель и машина — когда `order.vehicle.required` не `false`: `supplies_orders_vehicle_set` (навык
   `supplies-orders`).

## Шаг 8. Приёмка, этикетки, отчёт

- **Приёмка** — `supplies_cargo_rules_get`: только правила `applicable`/`required`; главный — `is_valid_distribution`
  (места совпадают с заявкой). Выполнено — «условия бесплатной приёмки выполнены» (прогноза в рублях нет ни в Seller AI,
  ни у Ozon — не говорить «0 ₽»); нет — починить до отгрузки по навыку `supplies-cargoes` (там же тарифы и факт
  начислений).
- **Этикетки** — после подтверждённых мест, одним набором на все поставки всех заявок, PDF на вид места
  (`supplies_cargo_labels_bundles_create`, порядок — навык `supplies-cargoes`). Все файлы — сразу, имена не менять;
  места без этикеток (`missing`) назвать.
- Количества плывут и после создания: через часы Ozon режет объём и отменяет отдельные поставки. Перед отгрузкой ещё раз
  `supplies_orders_get` и `supplies_cargo_rules_get`; этикеток должно быть столько же, сколько мест.
- **Отчёт**: заявки ссылками `[<order_number>](https://seller.ozon.ru/app/supply/orders/<order_id>)`; факт против плана
  и недобор по городам (итог = живые поставки + по 1 шт. на поставку к отмене); поставки к отмене в кабинете с причиной;
  таймслот (время точки отгрузки); приёмка; PDF этикеток; что сверить в кабинете (сроки годности Seller AI не отдаёт).
  Что пошло не так — прямо; «готово» — только после чтения заявки.

## Заявка уже подана — перераспределить количества

1. `supplies_orders_list` (`tab=preparation`, `search` — номер вида `12345678-1`). «Мои заявки» без номеров или поиск
   нашёл больше, чем имелось в виду, — показать и спросить один раз, с какими работаем.
2. План — `python3 scripts/supply_plan.py plan` по кластерам поставок заявки (точку не спрашивать); кластер повторяется —
   количества по поставкам выставлять явно.
3. `supplies_supply_items_set` по поставкам: сначала целевое значение, не прошло — на коробку меньше; поднять — только
   до грузомест. Дальше — шаг 7; план и факт — в отчёт. У заявки с таймслотом нужен `confirm_accuracy`: эффект
   (`lowers_shipped`, `raises_maximum`) показать и спросить один раз (навык `supplies-orders`).
4. Поставке нужно больше 30 коробок — сначала новая заявка на остаток в тот же кластер (шаги 4–6, слот как у основной),
   после её `succeeded` — состав поставки до `30 × коробка` (+ палеты × вместимость); затем места обеих.

## Запреты

- Не занижать объём, чтобы «сошлось»; не заканчивать фразой «остаток подадим позже».
- **1 шт. — не заглушка.** Поставку не везут (склад не берёт: `INBOUND_NO_CAPACITY` с лимитом 0, или так решил
  пользователь), а в заявке есть другие — как велит сообщение Seller AI: состав этой поставки → 1 шт.
  (`supplies_supply_items_set`), её отмену пользователь делает в кабинете Ozon (одну поставку API не отменяет); объём —
  по методу плана другим кластерам или новой заявкой. Поставка в заявке одна — отмена всей заявки, только после явного
  «да».
- Не отменять и не пересоздавать заявки без просьбы. Пробных заявок «для проверки» не создавать: заявка бронирует
  вместимость и слот, отмена бьёт по точности.

## Как говорить с пользователем

Результат — города, количества, коробки и палеты, даты слотов. Не показывать `supply_id`, `bundle_id`, `operation_id`,
`draft_id`, `calculation_id`, ID кластеров, технические имена складов (`КАЗАНЬ_РФЦ_НОВЫЙ`) и коды ошибок. Заявки —
ссылками, SKU — только в ссылке на товар, точки отгрузки — с адресом. Не «создаю черновик, жду success», а «Проверяю,
какие города примут товар»; не `NOT_AVAILABLE_MATRIX`, а «Челябинск не принимает этот товар». Промежуточный прогресс не
пересказывать.

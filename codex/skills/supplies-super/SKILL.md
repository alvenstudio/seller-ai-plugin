# Серия Super-заявок в запас без таймслота

Результат — серия реальных заявок с одинаковым распределением, точным количеством и заполненными грузоместами.
**Таймслот не выбирается**: пока его нет, правки количеств не влияют на «Точность отгрузок», дату пользователь выберет
позже.

Обычная подача со слотом — навык `supplies-create`, к серии её не применять. Сколько готово в поданных Super-заявках и
комплект из них — навык `supplies-kits`.

## Параметры серии

Параметры — только из текущего запроса: прошлая серия не разрешает новую, и из неё ничего не переносить (точку, объём,
фасовку, число заявок, срок).

- магазин, точная карточка и фасовка — `products_list` с `search`; у новой карточки `is_super` должен быть сейчас;
- число **новых** заявок (или копий) и объём одной копии: «ещё двадцать» — двадцать дополнительных, «всего двадцать» —
  с учётом поданных;
- штук в коробке и число коробок; палеты — только если пользователь их назвал; срок «годен до»;
- точка отгрузки (`supplies_dropoff_points_search`: `warehouse_id`, `type`, название, адрес) и её часовой пояс;
- ограничения по кластерам и период, на котором нужен выбор дат.

Проверить: объём = коробки × штук в коробке, всё целое и положительное. Копия делится на несколько заявок — показать
«N копий × G заявок = N×G реальных заявок», объём копии и серии; согласие на N заявок не превращать в N копий по
несколько заявок. Квота Ozon — 50 расчётов и 50 созданий заявок в час на аккаунт: 20 заявок по 1–2 расчёта укладываются;
больше — сказать, сколько займёт.

## Кластеры и количества

1. География — РФ и СНГ, если пользователь не ограничил. Кто примет — покажет первый расчёт (ниже).
2. Распределение — по долям рынка, не по продажам и запасу. ID кластеров — `supplies_clusters_list` (`cluster_id`,
   `name`). Доли Ozon, % заказов FBO (24.07–21.08.2026, источник и дату назвать в плане): Москва, МО и Дальние регионы
   22.77, Санкт-Петербург и СЗО 12.00, Ростов 6.25, Красноярск 5.49, Новосибирск 5.10, Казань 4.51, Дальний Восток 4.23,
   Екатеринбург 4.20, Ярославль 3.87, Уфа 3.46, Воронеж 3.46, Краснодар 3.07, Самара 2.99, Саратов 2.97, Тюмень 2.95,
   Невинномысск 2.38, Омск 2.07, Пермь 1.77, Оренбург 1.56, Махачкала 1.48, Тверь 1.21, Калининград 0.96, Астана 0.64,
   Беларусь 0.33, Алматы 0.28. Армении и Узбекистана нет — их долю задаёт пользователь. Свой рынок магазина (по просьбе)
   — `supplies_planning_sales_by_clusters` (`period=quarter`, `scheme=fbo`), `delivery_clusters[].units`.
   ```bash
   python3 scripts/super_plan.py allocate in.json   # {"total", "box_size", "shares": {cluster_id: доля}}
   ```
   Минимум одна полная коробка на кластер, остаток — по долям, сумма точная. Коробок меньше, чем кластеров, — показать
   достижимый охват. Ёмкость складов скрипт не знает: результат обязательно проходит расчёт.
3. Не больше 30 коробок в поставку: перевес — отдельной заявкой (k-я порция — в k-ю заявку), пересчитать число реальных
   заявок; коробки на палеты ради лимита не менять. Больше 20 кластеров — несколько заявок, у каждой своя проверка.

## Расчёт и календарь каждой заявки копии

1. `supplies_drafts_create` (`dropoff`, `clusters` с `units_per_box`; `deletion_sku_mode: PARTIAL` по умолчанию) →
   `supplies_drafts_calculate` → `supplies_drafts_get` до итога.
2. Принято ровно запланированное?
   ```bash
   python3 scripts/super_plan.py check in.json   # {"calculation": draft.calculation, "plan": {cluster_id: {sku: шт}}, "require_super": true}
   ```
   Нужно: все кластеры `full`, принятое по SKU (`accepted.items`) равно плану, исключённого (`restricted`) нет,
   `super: true`; `success` и `full` без количеств — не доказательство. Кластер не принимает целую коробку — исключить
   или ограничить его до подачи, объём перераспределить по долям между допустимыми и снова рассчитать на окончательных
   количествах. Расчёт принял 2 шт вместо 80 — не подавать в надежде поднять после создания.
3. Календарь — `supplies_drafts_timeslots_list` по точному набору кластеров, окнами не длиннее 27 дней; период не задан
   — ближайший месяц.
   ```bash
   python3 scripts/super_plan.py calendar in.json   # {"answers": [ответы окон], "date_from", "date_to"}
   ```
   → дни со слотами, самый длинный разрыв, пояс точки. Ошибка или непонятный ответ — не пустой календарь. Копия из
   нескольких заявок (остаток сверх 30 коробок, больше 20 кластеров) — `{"plans": [{"name", "answers"}, …], "date_from",
   "date_to"}`: по каждой заявке и `common` — дни, когда слот есть у всех (`same_slot_days` — с одинаковым слотом).
   Критерий — по `common`: широкие календари отдельных кластеров не доказывают широкий календарь объединения.
4. Критерий — выбор почти каждый день, а не одна поздняя дата, например «не менее 21 из 28 дней, без разрыва больше 3
   дней». Это ориентир плана, не лимит Ozon: записать в план и не снижать молча во время серии.
5. Календарь уже критерия — подозрительные кластеры рассчитать отдельными черновиками. Ограничивающий кластер — в
   отдельную заявку, если там выбор широкий; нет и отдельно — предложить исключить его, перераспределив объём. После
   любой правки состава снова проверить весь вариант. Из подходящих вариантов брать больший охват кластеров, затем большую
   долю рынка, затем меньше заявок; охват ценой календаря в 1–2 дня не покупать.

## План и согласие

- Таблица: кластер, доля, штуки, коробки, заявка. Итог: объём, копий и реальных заявок, исключения с причинами,
  календарь каждой заявки со временем проверки, явное «таймслот не выбирается».
- Метка Super — не цена: прогноза стоимости доставки нет ни в Seller AI, ни в API Ozon. «Бесплатно» не писать без сверки
  в кабинете Ozon.
- Просили сначала одобрить распределение — остановиться после плана.
- Полная просьба серии (товар, объём, фасовка, срок, точка, число заявок) — согласие на все копии и заполнение грузомест
  без повторных вопросов; план — в отчёт.
- Спросить один раз: чего-то не хватает; копия делится на несколько заявок, а пользователь говорил о N заявках; расчёт
  расходится с планом (кластер не берёт целую коробку, календарь уже критерия). Изменить распределение, объём, географию,
  упаковку или режим слота сверх согласованного — новое решение пользователя.
- Отменять заявки навык не разрешает. «Подай одну на пробу» — остановиться на ней: её успех не разрешает остальные копии.

## Подача — по одной копии, по очереди

1. Освежить Super товара (`products_list` → `is_super`). Свежий расчёт неизменного плана (живёт 30 минут: новый
   черновик или `supplies_drafts_calculate` по прежнему), `check` и календарь по критерию.
2. `supplies_orders_create`, `body: {draft_id, revision, calculation_id, timeslot: null, confirm: true}` — без
   таймслота. Итог — `operations_get` до `succeeded` с `order_id`; «создано» без `order_id` — ещё не заявка. Ozon требует
   дату (точность ниже 10 %) — записать причину и остановиться; слот не бронировать, чтобы потом снять.
3. Сверка: `supplies_orders_get` →
   ```bash
   python3 scripts/super_plan.py order in.json   # {"order": ответ supplies_orders_get, "plan": …, "dropoff_id": "…", "series_order_ids": […]}
   ```
   Проверяет Super, `timeslot: null`, точку, кластеры и штуки каждой поставки и что `order_id` новый (`series_order_ids`
   — заявки серии, созданные в этом разговоре). `composition_complete: false` — состав ещё не прочитан: подождать и
   перечитать. Расхождение — новые создания остановить.
4. Грузоместа каждой поставки — навык `supplies-cargoes` (срок — дата пользователя, не вычислять; `expected.cargo_ids` у
   новой поставки пустой). Затем `supplies_orders_get` (места и состав) и `supplies_cargo_rules_get`: все применимые
   правила; `expire_dates_presented` — факт срока, не дата; обязательное правило, которого навык не знает, — разобрать,
   не считать выполненным.
5. Перечитать Super, отсутствие слота и статус. Следующая копия — только после успешной сверки. `DATA_FILLING` после
   мест — разобрать причины; готовой заявку называть только в `READY_TO_SUPPLY`.

- Серию останавливают: пропал Super, календарь сузился ниже критерия, Ozon сократил количество. Созданное остаётся в
  отчёте. Не выбирать слот, не отменять заявку и не менять план, чтобы обойти ошибку.
- `outcome_unknown` — дубль не создавать: Seller AI сам ищет заявку по номеру черновика.
- **Возобновление серии**: черновики — `supplies_drafts_list` (`status=all`), операции — `operations_list`
  (`domain=supplies`), заявки — `supplies_orders_list` (`sort=created_at`, `order=desc`) и `supplies_items_list` (`sku`,
  `active=true`). Сверить созданное и подать только недостающие копии. Пометить заявки серии в Seller AI нечем — список
  `order_id` держать в разговоре и отчёте. Места у поставки уже есть: совпадают с планом — не перезаписывать (`replace`
  обнулит выданные этикетки); разошлись — остановиться и показать.

## Отчёт

Таблица со ссылками `[<order_number>](https://seller.ozon.ru/app/supply/orders/<order_id>)`: статус, товар, объём,
кластеры, грузоместа, Super, слот («не выбран»), итог проверки. Отдельно — созданные, полностью проверенные и
незавершённые; сколько осталось подать (заявок и штук). Календарь — со временем проверки: он ничего не бронирует и через
месяц может быть другим. Не обещать, что статус, срок заявки или бесплатность сохранятся до отгрузки. Этикетки — только
по просьбе, по навыку `supplies-cargoes` (набор по видам мест на поставки заявок, о которых просят). Создание заявок — не
отгрузка; подбор из серии потом — навык `supplies-kits`.

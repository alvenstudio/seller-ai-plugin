# Ежедневный отчёт по рекламе и продажам

Отчёт возвращается пользователю Markdown-таблицами в чат (Notion больше не нужен: история и сами данные — в Seller AI). Таблицу и
аномалии собирает `scripts/daily_report.py` из сохранённых ответов инструментов; решения по ставкам принимает агент, прочитав весь
контекст, — скрипт только собирает факты.

## 1. Данные

Магазин — `stores_list`: один — он, несколько — спросить (или «по всем» — сводка ниже); день — сегодня (МСК) или названный;
для периода те же шаги. Сначала `stores_ozon_access_get`: при `bidder_blind`, `performance_key_refused` или нерабочем ключе
Seller — сказать это первой строкой отчёта (данные рекламы или продаж неполные).

Сохранить в файлы ответы:

1. `promotion_analytics_get` — `slice=product`, `date_from`, `date_to` (все типы продвижения) → `products.json`. Строка товара:
   `metrics.expense` (весь расход), `sales` (продажи с рекламы), `gmv` (вся выручка товара по заказам), `drr_promo`, `drr` (общий ДРР),
   `ctr`, `clicks`, `orders`. `gmv.covered: false` — отправления периода не загружены, общий ДРР неизвестен.
2. То же с `types=cpc_search_reco,cpc_search,special` → `cpc.json`: расход на клики и средняя цена клика; CPO = всё − CPC.
3. `unit_economics_plan_list` (`scheme=FBO`) → `plan.json`: целевой ДРР товара — `inputs.drr` (доля; 0 — цель не задана).
4. Текущие ставки: `promotion_campaigns_list` (`states=RUNNING`, `page_size=100`) → `promotion_campaign_products_list` каждой
   кампании (`date_from`, `date_to` отчёта, `page_size=200`; файл на страницу) — `bid` товара и `bidder` (цель биддера в силе);
   `promotion_cpo_products_list` (`page_size=200`) → `cpo-*.json` — `enabled`, `display_bid_pct`, `display_bid_rub`. Каждый
   список — все страницы, пока не набран `total`: товар со второй страницы иначе останется без ставки, а товар биддера — с
   целью плана вместо цели биддера (скрипт назовёт недостающие страницы в «ДАННЫЕ НЕПОЛНЫЕ»).
5. Алерты биддера, которые решает продавец: `promotion_bidder_alerts_list` (`actionable=true`; по умолчанию — текущие) →
   `alerts.json`. Скрипт делает из них аномалии «БИДДЕР ПРОСИТ РЕШЕНИЯ» (кампания, товар, текст алерта), замолчавший биддер
   (`bidder_silent`: кампания крутится на последних ставках без контроля ДРР) — первой строкой. Рабочие заметки биддера
   (`actionable: false`: перерасход и снижение ставки, защитный режим, обучение) в аномалии не идут — он решает их сам.
6. Был ли уже отчёт за этот день в этом разговоре — его `products.json` передать как `--previous` (промежуточный срез).
   Срез — только в пределах разговора: снимков дня Seller AI не хранит (пока недоступно в Seller AI), отчёт из прошлого
   разговора не найти — так и сказать. Нужен пользователю — запрос функции (навык `feedback`).

```sh
python3 scripts/daily_report.py --products products.json --cpc cpc.json --plan plan.json \
    --campaign-products campaign-*.json --cpo cpo-*.json --alerts alerts.json \
    [--previous products_earlier.json] --strategy references/store-promotion-strategies.json \
    --store-name "<магазин>"
```

`--json` — те же данные для своей аналитики (строки, аномалии, сигналы, срез).

## 2. Отчёт

Заголовок — магазин, день и «данные Ozon на ЧЧ:ММ МСК» (`observed_at` ответа): отчёт за сегодня — срез на этот момент.
Порядок блоков (так и показывать):

1. **🚨 АНОМАЛИИ** — капсом, по деньгам (сколько потеряно), чтобы слив бюджета нельзя было пролистать. Ничего — «АНОМАЛИЙ НЕ
   НАЙДЕНО».

   | Аномалия | Условие |
   |---|---|
   | РАСХОД БЕЗ ПРОДАЖ | расход ≥ 500 ₽, выручка 0 |
   | ПЕРЕРАСХОД | общий ДРР выше цели больше чем на 1 п. п. и лишнее ≥ 300 ₽ |
   | ВЫСОКИЙ ДРР БЕЗ ЦЕЛИ | цели в юнит-экономике нет, общий ДРР > 40 % |
   | РЕКЛАМА БЕЗ ЗАКАЗОВ | расход ≥ 1 000 ₽, продаж с рекламы 0 |
   | КОНЦЕНТРАЦИЯ БЮДЖЕТА | один товар ≥ 50 % расхода магазина и при этом выше цели |
   | С ПРОШЛОГО СРЕЗА | расход прирос ≥ 300 ₽, а выручка нет, или ДРР прироста вдвое выше цели |
   | ПО МАГАЗИНУ | однодневный отчёт: ДРР магазина выше средневзвешенной цели, перерасход ≥ 300 ₽ |
   | ДАННЫЕ НЕПОЛНЫЕ | отправления не загружены, заказы моделей неизвестны, `warnings` ответов, переданы не все страницы списка |
   | БИДДЕР ПРОСИТ РЕШЕНИЯ | текущий алерт биддера из тех, что решает продавец (`actionable`); замолчавший биддер — первым |

   Товары с расходом меньше 300 ₽ в аномалии не попадают (шум). Ozon отдаёт рекламные продажи с задержкой — «реклама без заказов»
   срабатывает только на заметных суммах.
2. **Итого** — расход (CPC / CPO / ∑), продажи с рекламы, вся выручка, продано с рекламы, ДРР в продвижении, общий ДРР и цель
   магазина (средневзвешенная по выручке), CTR.
3. **По товарам** — расход CPC / CPO / ∑, продажи с рекламы и итого, CTR, конверсия клика в заказ, ДРР, ДРР общ. (⚠️ выше 40 %),
   цель, CPC ср. (средняя цена клика за период) и отдельными колонками текущие ставки: «CPC тек.» — по каждой активной
   кампании через « / » (у автостратегии Ozon — «авто», у «Целевого ДРР» Ozon — «ДРР N %», у топ-позиций — «Топ-N»;
   `NO_AUTO_STRATEGY` — ручная ставка, как `TARGET_BIDS`; «(б)» — ставку ставит биддер), «CPO %» и «CPO ₽» — ставка «Оплаты
   за заказ» (выключена — «выкл.»); последняя строка ИТОГО. Цель товара в кампании биддера — **цель биддера** в силе (своя,
   из плана или разгон; помечена «*»), а не ДРР плана: «ПЕРЕРАСХОД» и 🔴/🟢/🔵 считаются к ней. Числа с пробелами в
   тысячах и «₽», нули — «—».
4. **ДРР к цели** (однодневный отчёт): 🔴 выше цели больше +1 п. п., 🟢 в коридоре −2…+1, 🔵 ниже больше чем на 2 п. п.;
   ⚪ расхода за день нет — Ozon ещё не выложил статистику товара (или реклама не крутилась), это не «ниже цели»; ⚪ без
   цели — расход или выручка есть, а ДРР плана не задан (без цели нет ни сигнала, ни «ПЕРЕРАСХОДА»). В счётчики сводки ⚪ не
   входят.
5. **Наблюдения** — 3–5 строк: товар с наибольшим расходом и его доля, товары с ДРР > 40 %, лучший общий ДРР, лучшая конверсия.
6. **Промежуточный срез** — если был более ранний отчёт за тот же период: прирост выручки и расхода по товарам и ДРР прироста (⚠️
   выше 25 %), ИТОГО. Сравнивать только отчёты одинакового периода (день с днём).

Цены покупателя и «СПП / скидки Ozon» в отчёте нет: Seller AI цену покупателя не хранит (её нет в Seller API без Premium Pro).
Колонок «Заказы» и «Ср. цена» прежнего отчёта (все заказы товара из отправлений) тоже нет: за сегодня Seller AI их по
товарам не отдаёт; за прошедший день — `analytics_products_list` (`ordered_units`, `revenue`), если пользователь просит.

## 3. Аналитика ставок (по запросу или после отчёта)

Прочитать `references/general-promotion-strategy.md` и `references/store-promotion-strategies.json` (коридор, шаги, минимум расхода;
`stores.<store_id>` своей копии пользователя переопределяет `default_strategy`). Затем по каждому товару с расходом:

- все его **активные** кампании за клики: `promotion_campaigns_list` (`states=RUNNING`) → `promotion_campaign_products_list` каждой
  (все страницы, `page_size=200`):
  название, размещение, стратегия, `bid` (текущая), `bid_min`, `stats.avg_cpc` (средняя за период), у кампании биддера — `bidder`
  (цель, статус, обучение, последнее решение);
- «Оплату за заказ»: `promotion_cpo_products_list` — `enabled`, `display_bid_pct`, `reduced` (комбо), `carrots_status`;
  `promotion_cpo_all_get` — «все товары» и ставка;
- историю: `promotion_analytics_get` по дням (`days[]` товара) за 7 дней и `promotion_history_list` — кто и что менял;
- алерты товара и кампании: `promotion_bidder_alerts_list` (`sku`, `campaign_id`; `state=all` — и прошлые) — что биддер уже
  заметил (перерасход, ставка на минимуме, чужие изменения ставок) и с какого момента.

Рекомендацию писать **по каждой кампании отдельно** (название, «Поиск» / «Поиск и рекомендации», текущая ставка, сигналы); всегда
показывать текущий общий ДРР и целевой. По CPO — режим, а не рубли. Автостратегия — пометить, ручную ставку не считать. Кампания
биддера — советовать цель, «ДРР из плана», разгон, а не ставку.

## 4. Решения пользователя

1. Спросить, согласен ли пользователь. Не согласен и причина не названа — сначала попробовать вывести её из контекста, иначе коротко
   уточнить.
2. «Да» на рекомендацию с цифрами (кампания, товар, было → станет) — согласие на её команды; просьба сразу с цифрами («снизь
   ставку фиников до 9 ₽») — тоже. Выполнить (одна команда на намерение, `idempotency_key`, ждать `succeeded`; 202 —
   `promotion_operations_get`; `outcome_unknown` не отправлять повторно) и показать было → стало:
   - ставки ручных кампаний — `promotion_campaign_products_bids_set` (`items[{sku, bid, expected_bid}]`, целые рубли от `bid_min`);
   - цель товара в кампании биддера — `promotion_campaign_products_targets_set` (`target_total_drr` в процентах, `plan`, `ramp`);
   - выключить кампанию «Поиск и рекомендации» — `promotion_campaigns_deactivate` (ставка CPO комбо-товаров станет фиксированной:
     это должно быть в рекомендации, на которую пользователь сказал «да», иначе — сказать и спросить).
3. Итог решения (рекомендация, решение, почему, что учесть в следующий раз) — показать пользователю. Хранить стратегию
   магазина и подтверждённые уроки Seller AI пока не умеет (пока недоступно в Seller AI), а файлы опубликованного плагина
   пользователь не правит: правило, которое он подтвердил, агент предлагает записать в свои инструкции или память — вне
   плагина и без чужих данных. Пороги магазина, отличные от `default_strategy`, — своя копия
   `store-promotion-strategies.json` пользователя (`stores.<store_id>`), её передают в `--strategy` вместе с `--store-id`;
   в файл плагина ID магазинов не пишутся.

## Сводка по всем магазинам

`stores_list` → отчёт по каждому магазину; в чат — по магазину две-три строки (расход, общий ДРР, главная аномалия, счётчики
товаров к цели «🔴 N · 🟢 N · 🔵 N» однодневного отчёта) и общий блок аномалий всех магазинов по деньгам. Магазин, по
которому данных нет (ключ, `not_ready`), — так и написать, не «всё чисто». Регулярный (почасовой) прогон и рассылка — не
навык: планировщиков у навыков нет.
